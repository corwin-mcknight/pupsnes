# Test ROMs

PupSNES can build purpose-built SNES test ROMs directly from source in this repo using the real `cc65` toolchain: `ca65` assembles 65816 source and `ld65` links it into `.sfc` images. These ROMs are meant for bring-up and regression scenarios where we want small, auditable programs instead of opaque binary fixtures.

## Location

- Sources live in `testroms/`
- Built `.sfc` images are emitted to `build/<preset>/test-roms/`

## Build

Configure and build normally:

```sh
cmake --preset dev
cmake --build --preset dev
```

The test-ROM target is built automatically with the test binary, so CI and local test builds both produce the images.

If `ca65` / `ld65` are not installed, install `cc65` first.

## Layout

- `testroms/<rom_name>/<rom_name>.s`: real `ca65` assembly source, one folder per ROM
- `testroms/<rom_name>/<rom_name>.romspec`: dynamically loaded ROM progress metadata, colocated with its source
- `testroms/lorom-32k.cfg`: shared `ld65` linker config for a simple 32 KiB LoROM image
- `testroms/pupsnes.inc`: shared LoROM metadata/reset-vector boilerplate macros
- `src/tests/rom_integration_tests.cpp`: metadata-driven ROM execution harness and progress expectations

Each ROM source owns its program bytes and title field, while the common include owns the repeated LoROM metadata bytes and reset-vector segment. That keeps the repeated SNES image structure centralized without hiding the generated bytes behind a fake assembler layer.

## Progress Tracking

The ROM integration harness runs built `.sfc` images through the emulator's real reset path with a bounded cycle budget, then evaluates each ROM against explicit goal metadata:

- purpose
- cycle budget
- expected current status
- goal descriptions
- observable-state checks such as CPU registers or WRAM bytes

The harness recursively discovers `*.romspec` files under `testroms/` at runtime, so adding a new ROM scenario does not require editing C++ just to register it.

## `.romspec` Format

Each ROM gets a sidecar metadata file. Example:

```toml
rom_name = "reset_smoke"
title = "Reset Smoke"
purpose = "Verify reset-vector boot, immediate load, and a self-loop at the loop label."
why_expected_to_fail = "This ROM previously failed before BRA support existed."
cycle_budget = 94
expected_current_status = "pass"

[goal]
name = "loads-expected-accumulator"
description = "Accumulator low byte should retain the immediate value loaded after reset."
kind = "cpu_a8"
expected_value = 0x42

[goal]
name = "holds-at-loop-address"
description = "Program counter should stay parked at the BRA loop target once execution settles."
kind = "cpu_pc"
expected_value = 0x8003
```

Supported goal kinds:

- `cpu_a8`
- `cpu_pc`
- `cpu_sp`
- `cpu_dbr`
- `wram_byte`

Optional scenario fields:

- `initial_dbr` — override the reset-value DBR (e.g. `0x7E`) before the scheduler starts; useful for exercising instructions that observe DBR while there are no in-ROM instructions to set it.

All current scenarios are expected to pass. `why_expected_to_fail` retains the
historical blocker that the scenario originally covered, so a regression still
has useful context in its failure report.
